PREGUNTA 1: La importancia de 0.0.0.0

En el contexto de redes, 127.0.0.1 (localhost) se refiere únicamente a la interfaz de loopback interna del contenedor. Si Uvicorn escucha en 127.0.0.1, solo acepta conexiones que se originen dentro del propio contenedor. Como resultado, cualquier intento de conexión desde fuera (el host o desde otro contenedor) es ignorado porque el servidor no está escuchando en la interfaz de red pública del contenedor.

0.0.0.0 representa todas las interfaces de red disponibles en la máquina. Al usar este valor, le indicamos al servidor que escuche en todas las direcciones IP asignadas al contenedor. Esto es necesario para que el mapeo de puertos de Docker funcione: el tráfico que entra por el puerto expuesto del contenedor debe ser entregado a la aplicación interna, y para ello la aplicación debe estar escuchando en una interfaz capaz de recibir tráfico externo (la interfaz vinculada a la red del contenedor).
PREGUNTA 2: Redes internas y DNS de Docker

Dentro de un contenedor, localhost hace referencia a sí mismo (al propio contenedor). Si el frontend intenta llamar a http://localhost:8000, buscará el puerto 8000 dentro del contenedor del frontend, donde obviamente no hay ningún servicio corriendo, resultando en un error de conexión.

Docker Compose crea automáticamente una red virtual privada (bridge network) para cada proyecto. Dentro de esta red, Docker configura un servidor DNS interno. Cuando definimos servicios en el docker-compose.yml (como backend), Docker registra automáticamente ese nombre de servicio en su DNS interno. Por tanto, el nombre backend se resuelve a la dirección IP privada que Docker ha asignado al contenedor del backend dentro de esa red aislada.
PREGUNTA 3: Caché de capas y tiempos de construcción

Docker construye imágenes por capas, y si una capa no ha cambiado, Docker reutiliza la versión cacheada.

    El orden óptimo (actual): Al copiar solo el requirements.txt y luego instalar, la capa de RUN pip install solo se re-ejecuta si el archivo de requisitos cambia. Si solo modificas el código fuente (main.py), Docker detecta que los requisitos son iguales y salta directamente a la capa de COPY . ., haciendo la construcción instantánea.

    El orden invertido (Ineficiente): Si hacemos COPY . . primero, cualquier cambio en cualquier archivo del proyecto (incluyendo un comentario en main.py) invalida la caché de esa capa. Al invalidarse, todas las capas posteriores deben reconstruirse. Esto obligaría a reinstalar todas las librerías con pip install en cada pequeño cambio de código, aumentando drásticamente los tiempos de despliegue y consumo de ancho de banda.

PREGUNTA 4: Gestión de Secretos en Producción

La solución actual con .env es cómoda para desarrollo, pero tiene el riesgo principal de que, si el archivo se sube accidentalmente al repositorio o se deja en el sistema de archivos del servidor, cualquier usuario con acceso de lectura puede obtener las credenciales.

    Variables de entorno del shell: Se inyectan directamente al arrancar el contenedor. Riesgo: Son visibles en logs de procesos o inspección de contenedores. Adecuado para entornos de pruebas sencillos.

    Docker Secrets (Swarm): Los secretos se montan como ficheros en un sistema de archivos en memoria (/run/secrets/). Riesgo: Muy bajo, el secreto nunca toca el disco. Ideal para entornos empresariales medianos que usan Docker Swarm.

    Gestión externa (AWS Secrets Manager / Vault): Es el estándar de oro. El contenedor autentica su identidad ante el gestor y descarga el secreto en tiempo de ejecución. Entorno: Imprescindible en producción a gran escala (Cloud nativo), ya que permite rotación automática de llaves, auditoría de acceso y encriptación de extremo a extremo.
